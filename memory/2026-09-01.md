# 2026-09-01 — RAG chatbot demo-reliability bugs found and fixed (local only)

## Context
This is the streampulse half of the "demo reliability" problem: during the Ruchita Design
on-site (29 Aug), the RAG chatbot didn't respond properly when shown live. Per
`~/.claude/projects/-Users-uttkarshtyagi-job/memory/project_demo_reliability_gap.md`, this side
was "completely untouched" until this session.

## Investigation
Confirmed local Postgres (`gold` DB, 560,359 rows in `gold_chunks`) and Redis were both already
running, `DJANGO_ENV=dev` pointed at them, `python manage.py check` was clean. Ran the actual dev
server and POSTed a real question to `/api/v1/chatbot/messages/` — got back a **hardcoded canned
"demo mode" placeholder reply** in 39.5 seconds, not a real answer. That reproduced the reported
bug exactly.

## Three real, stacked bugs (each was hiding the next one)

1. **`GROQ_MODEL=llama-3.3-70b-versatile` was decommissioned by Groq** at some point after this
   project was built — confirmed via `GET https://api.groq.com/openai/v1/models`, that model ID
   is no longer in the list, so every call 404'd. **Fixed**: swapped to `qwen/qwen3.8-27b`
   (verified against the live model list, and confirmed it returns plain `content` immediately
   rather than burning the whole `max_tokens` budget on internal `reasoning` first the way the
   `openai/gpt-oss-*` models on Groq do — that would have needed a `max_tokens` bump too, same
   issue the code already documents for Gemini's "thinking" behavior).
2. **`_call_llm()`'s Gemini error handling didn't cover a plain 5xx.** It already caught 429 and
   timeout/connection errors (per an earlier fix, per the code's own comments) to fall through to
   Groq — but a genuine Gemini `503 Service Unavailable` (hit live, transient on Google's end)
   fell into the `else: raise` branch and killed the whole request before Groq ever got tried.
   **Fixed**: any `5xx` (500-599) is now treated the same as a timeout — try the next provider,
   don't mark the budget exhausted (a 5xx isn't evidence of quota exhaustion).
3. **`services.get_bot_reply()`'s bare `except Exception` swallowed everything with zero
   logging.** This is why bugs #1 and #2 were invisible from the outside — a live demo just
   looks like "the bot doesn't work," with no way to tell why without instrumenting it, which is
   exactly what happened at the Ruchita interview. **Fixed**: added `logger.exception(...)`
   before falling back to the canned reply, so any future failure that reaches this point shows
   up in the server logs (`journalctl`/gunicorn log on the EC2 box) without changing the graceful
   user-facing behavior.

## A fourth thing, found while verifying the fix: cold-start latency
Even after all three fixes, the very first request after a server (re)start took 23-39 seconds —
traced to `_get_model()` lazily loading the `all-MiniLM-L6-v2` SentenceTransformer weights from
disk on first use. Every request after that first one only took 3-8 seconds. This alone could
read as "broken" in a live demo if the interviewer's first-ever question happens to also be a
fresh gunicorn worker's first request.

**Fixed**: `apps/chatbot/apps.py`'s `ChatbotConfig.ready()` now spawns a daemon thread that calls
`rag._get_model()` at server startup, pre-loading the embedder before any real user request
arrives. Guarded so it only runs for an actual server process (`runserver`/`gunicorn` in
`sys.argv`) and, under the dev autoreloader, only in the reloaded child process (`RUN_MAIN=true`)
— not for `manage.py migrate`/`shell`/etc., and not doubled in the reloader's parent process.

## Verification
Restarted the dev server clean, confirmed the "Loading weights" log line appeared at startup
(not on first request), then sent real queries with no warm-up call first:
- Single-entity ("How did Kendrick Lamar perform in 2024?") — real grounded answer, 5 sources,
  ~8s first-request time (down from 23-39s).
- Comparison ("Compare India and Brazil") — real answer with a markdown table, ~3.7s (steady
  state).
- Aggregate ("Which country has the most streams?") — real SQL-routed answer, 1 source.
- Multi-turn follow-up ("What about Japan?" with prior history) — condensation kicked in
  correctly, real grounded answer, ~13s (extra LLM round-trip for condensation is expected here,
  not a bug).

All four returned real data-grounded answers with real `sources`, never the canned placeholder.
